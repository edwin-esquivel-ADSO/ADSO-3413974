💧 Plan A · Hidro Smart (Hallazgo #27)

El problema claro: En el servidor tenían tablas y fórmulas listas para calcular el ahorro de agua. Pero en la pantalla web pusieron 10 consejos fijos inventados ("cierra la llave", "báñate en 5 minutos") y dejaron escrito en el código: "esto no son recomendaciones reales". La pantalla nunca le pidió datos al servidor.

Visual de la Solución De Maqueta a Conexión Real
✕ Antes (Lo que vio el auditor):
Pantalla con textos fijos quemados en HTML.
🚫 Cable cortado: no llama a la base de datos.
➔
✓ Solución (Lo que implementamos):
La pantalla llama a GET /recommendations con el token del usuario.
⚡ Muestra datos vivos: "Tu hogar ahorró 140L este mes".
🚨 Por qué estaba mal

El usuario siempre veía lo mismo aunque gastara más agua. En la auditoría esto cuenta como flujo roto porque es una pantalla de cartón.

🛠️ Cómo lo solucionamos

Conectamos la pantalla a la base de datos usando el endpoint del servidor y consumimos la vista de resumen de ahorro calculada en PostgreSQL.

Endpoint / API Es la ventanilla del servidor donde la pantalla pide los datos reales.
Vista Materializada Una tabla pre-calculada en la base de datos para no poner lento el sistema sumando millones de gotas de agua.

🗣️ Plan B · One Language (Hallazgo #55)

El problema claro: Los compañeros trabajaron bastante en su rama de borrador (dev), pero la rama principal (main) la dejaron completamente vacía. Además, no tenían pruebas que revisaran que la traducción de señas funcionara y no tenían ningún robot que verificara si el código servía antes de subirlo.

Visual de la Solución Flujo de Ramas y Robot de CI
✕ Antes (Desorden en GitHub):
main: [Vacía] ╌╌ dev: [77 commits aislados]
🚫 Para el evaluador no había nada entregado formalmente.
➔
✓ Solución (Entrega Formal):
Robot de GitHub revisa: Compilación ✓ | Pruebas ✓
🚀 Fusión a main lista para desplegar y calificar.
🚨 Por qué estaba mal

En el SENA y en cualquier empresa, si el código no está en la rama main, se considera que no fue entregado. Y sin pruebas, cualquier cambio puede dañar la IA sin que nadie se entere.

🛠️ Cómo lo solucionamos

Pasamos el código de dev a main con un Pull Request ordenado, escribimos pruebas para el modelo y pusimos a GitHub Actions a probar todo automáticamente.

Rama main Es la vitrina del negocio: solo debe tener código probado y listo para funcionar.
CI (Integración Continua) Un vigilante virtual en la nube que prueba que nada esté dañado cada vez que subes un cambio.

🔐 Plan C · EcoRuteando (Hallazgo #83)

El problema claro: Para activar el código de 6 dígitos del celular (segundo factor 2FA), el sistema crea una clave secreta. El error fue que para pintar el dibujo del código QR, le mandaron la clave secreta por internet a una página ajena (qrserver.com). Es como mandarle la clave del banco a un desconocido para que te la imprima en un sticker.

Visual de la Solución Protección Total del Secreto 2FA
✕ Antes (Fuga Peligrosa):
Celular envía clave secreta ➔ Servidor público desconocido.
🚫 Un hacker o esa página podían clonar los códigos de acceso.
➔
✓ Solución (Seguridad en Casa):
La app dibuja el QR directamente en la pantalla del celular.
🔒 La clave secreta nunca sale a internet ni se comparte con nadie.
🚨 Por qué estaba mal

Es una falla crítica de seguridad. Si el dueño de esa página externa o alguien intercepta la red, puede clonar los códigos del celular y entrar a cualquier cuenta.

🛠️ Cómo lo solucionamos

Instalamos una librería dentro de la propia app (qrcode.react) para pintar el QR localmente en pantalla, bloqueamos llamadas a páginas raras y cambiamos las claves expuestas.

TOTP / 2FA El código numérico temporal que cambia cada 30 segundos en Google Authenticator.
Generación Local Dibujar la imagen directamente en la memoria del teléfono sin enviar datos a la nube.

🏁 Conclusión de Nuestra Revisión

Esta auditoría nos enseña que el software no solo debe "verse bonito", sino que debe cumplir con las reglas reales de la industria:

1. Datos Reales

Las pantallas deben hablar siempre con la base de datos a través de servicios reales. Nada de datos fijos o maquetas para disimular.

2. Entregas Claras

El código tiene que estar en la rama oficial (main), con pruebas que certifiquen que funciona antes de mostrarlo al público.

3. Cero Fuga de Claves

Las claves y contraseñas no se envían a páginas de terceros. Todo lo que sea seguridad se procesa de forma hermética y local.

✓ Con estas 3 soluciones aplicadas, los flujos quedan completos, seguros y listos para calificación.
